# VPN이란 무엇일까?

사무실 안에서 VPN을 켜놓은 채 작업하다가 GitHub, Claude 등 외부 서비스에 접속이 안 되는 증상을 겪었다.
DNS는 정상이었는데 TCP 연결 단계에서 막혔고, 사파리는 됐는데 크롬만 안 됐다.
결국 원인은 "사내망에서 굳이 VPN을 켜놓은 것"이었고, VPN을 끄자마자 정상적으로 접속됐다.

이 사고를 계기로 VPN이 실제로 어떻게 동작하는지, 언제 써야 하고 언제 끄는 게 맞는지 제대로 이해하고 싶었다.
같은 증상을 다시 마주쳤을 때 스스로 진단할 수 있도록 계층별 확인 방법도 함께 정리한다.

## VPN의 본질

VPN은 Virtual Private Network, 가상 사설망이다.

"사설망(Private Network)"은 외부 인터넷에서 직접 접근할 수 없는 내부 네트워크다.
회사의 개발 서버, 내부 도메인, DB 접근 등이 여기에 해당한다.

문제는 집에 있는 개발자가 회사 사설망에 접근해야 할 때다.
집과 회사는 물리적으로 다른 네트워크에 있기 때문에, 그냥은 접근할 수 없다.

VPN은 이 문제를 "가상(Virtual)"으로 해결한다.
실제로는 집에 있지만, 마치 사무실 내부 네트워크에 연결된 것처럼 만들어주는 기술이다.

## VPN의 동작 원리

### 터널링

VPN의 핵심 메커니즘은 터널링(Tunneling)이다.

터널링이란 클라이언트와 VPN 서버 사이에 암호화된 전용 통로를 만드는 것이다.
이 통로 안에서 주고받는 패킷은 외부에서 내용을 볼 수 없다.

동작 흐름을 단순화하면 다음과 같다.

```
[집 PC] → (암호화된 터널) → [VPN 서버 (회사 내부)] → [회사 내부 서버]
```

클라이언트가 VPN에 연결하면

1. 클라이언트의 네트워크 인터페이스에 가상 NIC(TUN 디바이스)가 생성된다.
2. 이 가상 NIC를 통해 나가는 트래픽은 VPN 클라이언트가 가로채 암호화한다.
3. 암호화된 패킷은 실제 인터넷을 통해 VPN 서버로 전달된다.
4. VPN 서버가 복호화 후 목적지로 전달한다.

외부에서 보면 집 PC가 VPN 서버 하나에만 연결하는 것처럼 보이고,
내부에서 보면 집 PC가 회사 내부망에 직접 연결된 것처럼 동작한다.

> **TUN vs TAP**
>
> 가상 NIC에는 TUN과 TAP 두 종류가 있다.
> - **TUN**: Layer 3(IP 패킷) 단위로 동작. WireGuard는 TUN 전용이고, OpenVPN도 TUN이 기본이다.
> - **TAP**: Layer 2(이더넷 프레임) 단위로 동작. 이더넷 브리징이 필요한 구형 환경에서 쓴다.
>
> 일반적인 원격 접속 VPN은 TUN이다.

### IP 주소는 어떻게 바뀌나

VPN에 연결하면 회사 내부 IP 대역의 주소가 새로 할당된다.

예를 들어,
- 집 공유기 IP: 192.168.0.100 (집 내부망)
- VPN 연결 후 가상 IP: 10.10.0.25 (회사 VPN 대역)

이렇게 되면 라우팅 테이블이 변경된다.
회사 내부 대역(10.10.0.0/24 등)으로 향하는 트래픽은 가상 NIC를 통해 VPN 터널로 나가고,
그 외 트래픽은 Full Tunneling 여부에 따라 달라진다.

## Full Tunneling vs Split Tunneling

VPN에는 두 가지 모드가 있다.

**Full Tunneling**은 모든 인터넷 트래픽을 VPN 터널로 보낸다.

```
github.com 접속 요청
→ VPN 터널을 통해 회사 VPN 서버로
→ 회사 VPN 서버에서 인터넷으로 나감
→ github.com 응답이 다시 VPN 터널을 통해 집으로
```

google.com 같은 외부 서비스를 이용할 때도 회사 망을 경유한다.
보안 통제가 강력하지만, 불필요한 트래픽이 회사 망을 거치게 된다.

**Split Tunneling**은 회사 내부 대역 트래픽만 VPN으로 보내고, 나머지는 직접 인터넷으로 보낸다.

```
github.com 접속 요청 → 직접 인터넷으로
10.10.0.5 (회사 내부 서버) 접속 요청 → VPN 터널로
```

어느 모드가 기본값인지는 VPN 제품과 회사 보안 정책에 따라 다르다.
상업용 VPN(NordVPN 등)은 Full Tunneling이 기본인 경우가 많고,
기업 VPN은 제품마다 다르다. 보안을 우선시하면 Full, 트래픽 효율을 고려하면 Split을 선택한다.
이 차이가 "사무실 안에서 VPN을 켜면 안 되는 이유"와 직결된다.

## 언제 VPN을 써야 하는가

VPN은 "외부에서 내부망으로 들어가야 할 때" 사용하는 도구다.

서버 개발자 기준으로 VPN이 필요한 상황은 다음과 같다.

- 집에서 회사 개발 환경 도메인에 접속해야 할 때 (ex. `api.internal.company.com`)
- 재택근무 중 회사 내부 DB, 서비스에 접근해야 할 때
- 카페나 공공 와이파이에서 회사 내부 인프라를 안전하게 사용해야 할 때

반면 VPN이 불필요한 상황도 있다.

- 사무실 안에 있을 때 - 이미 내부망에 있다
- 회사 라우터를 통해 인터넷에 연결되어 있을 때 - 보안 장비가 이미 앞에 있다

## 사무실 안에서 VPN을 켜면 안 되는 이유

### 불필요한 라우팅 왕복

사무실 안의 PC는 이미 회사 내부망에 있다.
여기서 VPN(Full Tunneling)을 켜면 아래와 같은 경로가 만들어진다.

```
[사무실 PC] → [VPN 서버 (같은 내부망)] → [다시 내부망 or 인터넷]
```

github.com에 접속하려면

```
사무실 PC (192.168.1.100)
→ VPN 서버 (10.10.0.1, 같은 사무실 내부)
→ VPN 서버에서 인터넷으로 나감
→ github.com 응답이 VPN 서버로 들어옴
→ 다시 암호화해서 사무실 PC로
```

같은 건물 안에서 일부러 우회로를 만드는 셈이다.
불필요한 레이턴시와 VPN 서버 부하가 생기고, 더 중요하게는 IP 대역이 꼬일 수 있다.

사무실 PC는 이미 `192.168.1.x` 대역을 쓰고 있고, VPN이 `10.10.0.x` 대역을 추가로 할당한다.
라우팅 테이블에서 두 대역이 충돌하거나 예상치 못한 경로로 패킷이 라우팅될 수 있다.

### 보안 솔루션과의 충돌

회사 사무실에는 라우터나 방화벽 같은 보안 장비가 이미 배포되어 있다.
여기에 VPN까지 켜면 패킷이 통과하는 보안 장비의 구성이 달라진다.

Full Tunneling 상태에서는 트래픽이 VPN 서버를 통해 나가기 때문에,
평소에는 직접 나가던 트래픽이 VPN 서버를 경유하는 새로운 경로를 타게 된다.
회사의 보안 솔루션은 이 변화를 이상 경로로 감지하거나,
VPN 터널 내 트래픽에 별도의(더 제한적인) 보안 정책을 적용할 수 있다.
이것이 평소에는 되던 외부 접속이 VPN을 켜는 순간 막히는 이유다.

## 이번 장애 분석

### DNS는 정상, TCP는 실패

장애 당시 증상을 계층적으로 분석해보면 다음과 같다.

```
nslookup github.com → 20.200.245.247 (정상)
```

DNS 계층은 문제없이 IP를 반환했다.
즉, 이름 해석(Domain → IP)은 동작했다.

그런데 그 이후 실제 연결이 실패했다.
이는 TCP 핸드셰이크 단계(IP로 연결을 맺는 과정)에서 패킷이 차단됐다는 뜻이다.

```
DNS 조회 (UDP 53) → 성공
TCP 연결 (TCP SYN) → 실패 (패킷 차단)
```

네트워크 계층 관점에서 이것은 중간 어딘가(방화벽, 보안 솔루션)가
특정 목적지로의 TCP 연결을 차단하고 있다는 신호다.

VPN을 켠 상태에서 트래픽 경로가 바뀌어, 평소에는 통과하던 보안 장비에서 차단이 발생한 것으로 볼 수 있다.

### 크롬만 안 됐던 이유

사파리는 됐는데 크롬만 안 됐다는 점이 흥미롭다.
이는 브라우저가 단순 HTTP 클라이언트가 아니라, 보안 정책이 적용되는 관리 대상이기 때문이다.

`chrome://policy` 를 확인했을 때 트러스가드(TrusGuard, 회사에서 배포한 엔드포인트 보안 솔루션) 관련 정책이 배포되어 있었다.
회사가 Chrome Enterprise를 통해 보안 정책을 브라우저에 직접 배포한 것이다.

```
UserSecuritySignalsReporting
UserSecurityAuthenticatedReporting
```

이러한 정책이 배포된 크롬은 보안 솔루션의 통제를 받는다.
VPN으로 트래픽 경로가 바뀐 상태에서, 보안 솔루션이 인증되지 않은 경로로의 접근을 차단했을 가능성이 높다.

사파리는 이런 정책이 배포되지 않아 정상 동작했고,
CLI(curl)가 안 됐던 것은 시스템 레벨의 라우팅 문제가 함께 있었을 수 있다.

> ### Tip
>
> 크롬이 안 되고 사파리는 되는 증상이 나타나면, `chrome://policy` 에서 회사 배포 정책을 먼저 확인해볼 것.
> 보안 정책이 배포된 크롬은 일반 브라우저와 다르게 동작한다.

## 네트워크 계층별 진단법

이번 장애를 계기로 비슷한 증상을 다시 마주쳤을 때 활용할 수 있는 계층별 진단 방법을 정리한다.
계층을 나눠 순서대로 확인하면 원인 범위를 좁히는 데 효율적이다.

**1단계: DNS 확인**

```bash
nslookup github.com        # DNS 조회, IP 반환 확인
dig github.com +short      # 더 간결하게 IP만 확인
```

IP가 정상적으로 반환되면 DNS 계층은 정상이다.

**2단계: TCP 연결 확인**

```bash
curl -v https://github.com  # 연결 과정을 단계별로 출력
```

`* Trying <IP>...` 이후 `* Connected` 가 나오면 TCP 연결 성공.
타임아웃이나 `Connection refused` 가 나오면 TCP 레벨에서 막힌 것이다.

**추가 확인: DNS 캐시 초기화**

DNS 캐시가 오래된 값을 물고 있으면 엉뚱한 IP로 요청이 갈 수 있다.
증상 해결이 안 될 때 한 번 시도해볼 만하다.

```bash
# macOS DNS 캐시 초기화
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
```

**계층별 증상 정리**

| 증상 | 의심 계층 | 확인 방법 |
|------|-----------|-----------|
| DNS 쿼리에 IP가 안 나옴 | DNS | `nslookup`, `dig` |
| IP는 나오는데 연결 안 됨 | TCP/방화벽 | `curl -v` → `Connection refused` 또는 타임아웃 확인 |
| 작은 요청은 되는데 큰 파일 전송이 끊김 | MTU/패킷 단편화 | `ping -D -s 1400 <target>` (macOS), `ping -M do -s 1400 <target>` (Linux) |
| VPN 연결 중인데 내부 도메인이 NXDOMAIN | DNS 리크 | `sudo tcpdump -i any port 53` (macOS에서 VPN 진단 시 `utun0` 등 터널 인터페이스 직접 지정 권장) |
| 연결은 되는데 내용이 안 옴 | TLS/HTTP | `curl -v` → TLS 핸드셰이크 실패 메시지 확인 |
| 특정 브라우저만 안 됨 | 브라우저 정책 | `chrome://policy` |

## 정리

VPN은 공개 인터넷에서 사설망으로 안전하게 접속하기 위한 기술이다.
터널링을 통해 암호화된 통로를 만들고, 클라이언트에게 내부 IP를 할당해 로컬 네트워크처럼 쓰게 한다.

사무실 안에서는 VPN이 필요 없다. 이미 내부망에 있기 때문이다.
오히려 VPN을 켜면 트래픽이 불필요하게 우회하고, 보안 솔루션이 변경된 경로를 이상으로 감지해 접속 장애를 유발할 수 있다.

네트워크 문제를 마주쳤을 때는 DNS → TCP → TLS → HTTP 계층 순으로 범위를 좁혀가는 것이 핵심이다.
DNS가 정상이면 IP 이후 계층의 문제다.
특정 브라우저만 안 된다면 브라우저에 배포된 정책을 의심해라.

> ### 요약
>
> VPN은 공개 인터넷을 통해 사설망에 안전하게 접속하기 위한 기술이다.
> 집에서 회사망에 붙을 때처럼 "밖에서 안으로 들어가야 할 때" 쓰는 것이지,
> 이미 사무실 안에 있다면 켤 이유가 없다.
